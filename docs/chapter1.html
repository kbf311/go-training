Chapter 01

なぜNext.js × Goなのか？

Next.js単体（Route Handlers / Server Actions）と比べたGoバックエンドの強みと、システム構成

1-1 なんでGoか（Next.js単体より何がいいのか？）

Next.js（App Router）は非常に強力で、Route HandlersやServer Actionsを使えば、Node.js上でDBアクセスを含むバックエンドAPIをすべて完結させることも可能です。

では、なぜわざわざGo言語でバックエンドを独立して作るのでしょうか？ 主な理由は以下の4点にあります。

⚡ 圧倒的な実行速度と省メモリ

Goは機械語に直接コンパイルされる言語です。Node.jsのような巨大なV8ランタイムが不要なため、起動はミリ秒単位、アイドル時のメモリ消費も数十MB程度で、高負荷なAPIリクエストを瞬時に捌きます。

🔀 強力かつ軽量な並行処理

Goの真骨頂である goroutine（ゴルーチン）は、OSスレッドよりもはるかに軽量（数KB）に動作します。数万件の並行リクエストや外部APIへの一括並行アクセスも極めて簡単に実装できます。

📦 「単一バイナリ」配布の手軽さ

go build で生成されるのは、依存ライブラリを内包した1つの実行ファイル（api.exe 等）だけです。node_modules のような重い依存関係の配置やバージョン不整合に悩まされません。

🎯 フロントとバックの責務分離

画面の頻繁なデザイン変更やUI要件はNext.jsで素早く対応し、ビジネスロジック・DBトランザクション・認証などの根幹は堅牢なGoで守るという、明確なチーム・システム分担が実現します。

Next.js単体構成 vs Next.js + Go構成 比較

観点 Next.js 単体 (Node.js) Next.js + Go 構成
言語・エコシステム TypeScript一元化（学習コスト低） TypeScript + Go（用途に特化した最適化）

デプロイ・配布 node_modules やコンテナが必要 Go側はバイナリ1個を配置するだけ
重い処理・並行処理 シングルスレッド（Workerが必要） Goroutineで数十万並行も余裕で処理

🐍 Python + Python (FastAPI / Flask) との違い

PythonはAI・機械学習ライブラリが最も充実していますが、GIL（グローバルインタプリタロック）によりCPUマルチコアを活かした並行処理が苦手です。AIの推論を呼び出す用途ならPythonが第一候補ですが、「何万件もの同時アクセスを低レイテンシ・低メモリで捌くAPI」としてはGoが圧倒的なパフォーマンスを発揮します。

☕ Next.js + Java (Spring Boot) との違い

Javaはエンタープライズで数十年の実績がありますが、JVM（仮想マシン）が重く、コンテナ起動に数十秒かかり、メモリも平気で数百MB〜GB単位で消費します。GoはJavaと同等の型安全性と実行速度を持ちながら、起動時間は数ミリ秒、メモリ消費は10分の1以下でコンテナやクラウド環境（AWS ECS/Fargate等）のコストを激減させます。

🤖 Next.js + Python (FastAPI) との違い

モダンなReact UIとAI/LLMバックエンドを組み合わせる現場では非常に人気のある構成です。ただし、API自体のスループットやサーバー維持コスト、単一バイナリ配布などの運用性ではGoに軍配が上がります。「AI主体の機能はPython、トランザクションや高頻度データ処理はGo」というマイクロサービス連携もよく採用されます。

⚡ Next.js + Next.js (Node.js単体) との違い

TypeScript一元化は初期開発が最も速いメリットがあります。しかしプロジェクトが育つにつれ、Node.jsのメモリ増大、長時間のバッチ処理でのCPU詰まり、node_modulesのセキュリティ脆弱性更新などの課題に直面します。Goをバックエンドに切り出すことで、画面の変更頻度とDB/ビジネスロジックの安定性を分離できます。

💎 Ruby on Rails との違い

Railsは「設定より規約（CoC）」で爆速プロトタイピングが可能です。しかし動的型付け言語ゆえに、コードベースが数万行を超えると型エラーの不安やリファクタリングの難しさが増します。Next.js (TypeScript) + Go は双方とも静的型付けのため、コンパイル時に不具合の大半を検知でき、長期運用に抜群の強さを誇ります。
